# KPIMS — معماری سامانه (Architecture)

**KPIMS — Kosar Production & Inventory Management System**
سامانه برنامه‌ریزی تولید و مدیریت موجودی — کارخانه قطعات فلزی خودرویی

## ۱) نمای کلی

```
┌────────────────────────────┐        ┌─────────────────────────────────┐
│  Frontend (React SPA)      │  HTTP  │  Backend (Express REST API)     │
│  React 19 + TypeScript     │──────▶ │  Node.js + Express 5 + Zod      │
│  Vite · RTL · Vazirmatn    │ /api/* │  JWT Auth · RBAC · Services     │
│  Jalali display (Intl)     │        │  Prisma Client                  │
└────────────────────────────┘        └───────────────┬─────────────────┘
                                                      │ Prisma ORM
                                              ┌───────▼────────┐
                                              │  PostgreSQL 17 │
                                              │  39 جدول — 4 دامنه │
                                              └────────────────┘
```

- **Frontend**: فقط نمایش و ورودی داده؛ **هیچ محاسبه‌ای از موجودی رسمی در فرانت انجام نمی‌شود**.
- **Backend**: تمام تراکنش‌های انبار و تولید، اعتبارسنجی Zod، RBAC، شماره‌گذاری اسناد و
  به‌روزرسانی موجودی رسمی (در فازهای بعد) همه سمت سرور.
- **Database**: منبع یکتای حقیقت؛ قیدهای یکپارچگی در سطح دیتابیس (FK / UNIQUE / CHECK).

## ۲) لایه‌ها و مرز مسئولیت‌ها

| لایه | مسیر | مسئولیت | ممنوع |
|---|---|---|---|
| UI | `frontend/src` | ناوبری، فرم‌ها، نمایش جلالی، state کلاینت | محاسبه موجودی، دسترسی مستقیم DB |
| API | `backend/src/routes`, `modules/*` | HTTP، اعتبارسنجی ورودی، کد وضعیت | منطق چند-جدولی بدون تراکنش |
| Business logic | `backend/src/services/*` | قواعد کسب‌وکار (شماره سند، قطع‌بوش، موجودی) | فرض اعتماد به ورودی UI |
| Data access | `backend/prisma/schema.prisma` + `config/db.ts` | اسکیما، کلاینت Prisma | SQL پراکنده بدون `@map` |

جریان یک درخواست:

```
Client → /api/v1/... → helmet/cors → json → requestLogger
       → authenticate (JWT) → requirePermission (RBAC)
       → zod schema.parse → service (db.$transaction) → response JSON
       → errorHandler (ZodError/PrismaError/ApiError → پیام فارسی)
```

## ۳) تصمیم‌های کلیدی طراحی

### 3.1) موجودی رسمی فقط سمت سرور
موجودی رسمی در جدول `stock_balances` نگهداری می‌شود و **فقط در همان تراکنش دیتابیسِ
قطع‌بوشِ سند** به‌روزرسانی می‌شود (الگوی آینده: `db.$transaction` → درج
`inventory_transactions` → upsert `stock_balances`). فرانت هرگز موجودی «محاسبه‌شده» را
نمایش منفی‌کار نمی‌دهد.

### 3.2) دفتر کل تغییرناپذیر (Immutable Ledger)
- رکوردهای `inventory_transactions` پس از درج تغییر نمی‌کنند و حذفشان با
  `ON DELETE RESTRICT` روی همه FKها مسدود است.
- اصلاح فقط با **سند ابطال**: تراکنش جدیدی که با `reversal_of_id` به رکورد اصلی اشاره می‌کند
  (`chk_inv_tx_reversal_self` اجازه self-reference به خود را نمی‌دهد).
- `posting_status` جدا از `status` است: گردش کار سند (پیش‌نویس/تأیید/لغو) با اثر
  حسابداری (قطع‌بوش‌نشده/قطع‌بوش‌شده/ابطال‌شده) قاطی نمی‌شود.

### 3.3) شماره‌گذاری اسناد یکتا
جدول `document_sequences` + سرویس `generateDocumentNumber(tx, key)` با
`SELECT ... FOR UPDATE` **داخل تراکنشِ خود سند**؛ دو قطع‌بوش هم‌زمان هرگز شماره تکراری
نمی‌گیرند. سیاست `YEARLY` با سال جلالی ریست می‌شود (شروع نمونه: `INV-001001`).

### 3.4) انواع داده
- کمیتی/وزن: `DECIMAL(18,4)` — هرگز float.
- PK: `UUID` (مناسب یکپارچگی ERP و جلوگیری از شماره‌گذاری قابل حدس).
- زمان: `TIMESTAMPTZ(6)` در UTC؛ تاریخ‌های کاری: `DATE` و نمایش جلالی در UI/سرویس.
- XOR قطعه/ماده با CHECK در سطح DB: `num_nonnulls(part_id, material_id) = 1`.

### 3.5) تقویم جلالی
- سرور: `Intl.DateTimeFormat('fa-IR-u-ca-persian')` با `APP_TIMEZONE` (پیش‌فرض `Asia/Tehran`) —
  بدون وابستگی خارجی؛ برای شماره‌گذاری سالانه هم استفاده می‌شود.
- کلاینت: همان روش با `VITE_APP_TIMEZONE` تا نتیجه مستقل از منطقه زمانی مرورگر باشد.

### 3.6) احراز هویت و RBAC
- `POST /api/v1/auth/login` → JWT (HS256) با `sub/username/role`، TTL قابل تنظیم
  (`JWT_ACCESS_TTL`, پیش‌فرض ۸ ساعت). هش گذرواژه با bcrypt.
- `authenticate` میدل‌ور: JWT را verify و **پروفایل تازه** کاربر (نقش + مجوزها) را از DB
  می‌خواند؛ غیرفعال‌شدن کاربر/نقش بلافاصله اعمال می‌شود.
- `requirePermission('module.action')` روی هر endpoint حساس؛ مجوزها در جدول
  `permissions` با الگوی `module.view|manage|post` و اتصال چند-به-چند `role_permissions`.
- لاگین موفق/ناموفق و رویدادهای مهم در `audit_logs` ثبت می‌شود.

### 3.7) نسخه‌بندی مسیر تولید
`part_routes(version)` با `UNIQUE(part_id, version)` و زنجیره `superseded_by_id`؛
وضعیت `DRAFT → ACTIVE → RETIRED`. دستور کار (`manufacturing_orders.route_id`) به نسخه
خصوصی اشاره می‌کند تا تغییر مسیر، سابقه تولید را خراب نکند.

### 3.8) آماده‌سازی برای ERP (SAPCO/سایر)
- نام جداول/ستون‌ها snake_case و پایدار؛ enumها جداول نوعی معتبر PostgreSQL.
- `reference_type/reference_id` در سند انبار برای اتصال چندریختی به اسناد مبدأ
  (گزارش تولید، قرارداد ماده) — بدون FK تا فازهای بعد آزادانه گسترش یابد.
- `material_lots` ردیابی بچ ورق‌های SAPCO را از روز اول ممکن می‌کند.

## ۶) موتور قطع‌بوش انبار (فاز دو)

جریان قطع‌بوش سند انبار — همه گام‌ها در یک تراکنش دیتابیس با ایزولاسیون `SERIALIZABLE`:

```
createDocument (DRAFT)  ──▶  postDocument ──────────────────────────────▶ POSTED
     │ بدون اثر بر موجودی          │ ۱. قضبه ضد قطع‌بوش تکراری
     │                             │    (UPDATE … WHERE posting_status='UNPOSTED')
     │                             │ ۲. ساخت حرکت‌ها به‌تفکیک نوع سند
     │                             │ ۳. برای هر حرکت: کنترل موجودی منفی «از دفتر کل»
     │                             │    ⟶ به‌روزرسانی StockBalance (کلید قطعی balanceKey)
     │                             │ ۴. درج ردیف تغییرناپذیر InventoryTransaction
     │                             │ ۵. به‌روزرسانی لوت / قرارداد SAPCO / رزرو
     │                             │ ۶. رکورد AuditLog
reverseDocument ──▶ سند ابطالی جدید (آینه تراکنش‌های اصلی، ارجاع reversal_of_id)
```

قواعد تضمین‌شده:
1. موجودی رسمی فقط از تراکنش‌های قطع‌بوش‌شده (projection دفتر کل) — در `applyStockMovement`
   کنترل منفی‌شدن از جمع دفتر کل انجام می‌شود، نه از خود ردیف موجودی.
2. سند پیش‌نویس هرگز بر موجودی اثر ندارد.
3. کلید موجودی: `part|material|warehouse|location|lot|unit|ownership|quality`
   — تفکیک ورق امانی SAPCO و قرنطینه کیفیت در سطح سطر موجودی.
4. ابطال فقط با سند ابطالی؛ سند قطع‌بوش‌شده ویرایش/حذف نمی‌شود.

## ۷) موتور تولید و WIP (فاز سه)

- **تولید عملیات**: از مراحل مسیر تولید ACTIVE قطعه، با برنامه مقدار معکوس
  `qty_i = Q / Π(1 − sf_j)` برای جبران ضایعات هر مرحله.
- **گزارش تولید**: تساوی اجباری `ورودی = تولید + مردود + بازکار + ضایعات`؛
  کنترل خوراک: `Σورودی ≤ Σدریافتی + Σبازکار` (بازکار قابل تغذیه مجدد است).
- **انتقال بین عملیاتی**: تنها راه جابه‌جایی مقدار؛ کنترل «آماده انتقال» =
  `تولید − منتقل‌شده`؛ انتقال به انبار محصول، رسید PRODUCTION_RECEIPT قطع‌بوش‌شده می‌سازد.
- **سازگاری مقادیر**: `دریافتی اول = محصول تکمیلی + ضایعات/مردود + WIP باقی‌مانده`
  — با endpoint `/api/v1/wip/reconciliation` و آزمون خودکار بررسی می‌شود.

## ۸) موتور برنامه‌ریزی تولید (فاز چهار)

**اصل بنیادی:** خروجی برنامه‌ریزی «پیشنهاد» است و هرگز مستقیماً سند تولید/انبار نمی‌سازد.
اجرای موتور فقط یک `ProductionPlan` با وضعیت `DRAFT` می‌سازد؛ تأیید (CONFIRMED) یک اقدام
کاربر با مجوز `planning.post` است و حتی پس از آن، ساخت دستور کار همچنان اقدام جداگانه در
ماژول تولید با ارجاع `planLineId` است. تغییر برنامه = نسخه جدید (`version`, `revision_of_id`)،
نسخه‌های پیش‌نویس قبلی `SUPERSEDED` می‌شوند و برنامه‌های تأییدشده دست‌نخورده می‌مانند.

**خط لوله محاسبه (همه در یک تراکنش دیتابیس — اسنپ‌شات سازگار):**

1. **تقاضای ناخالص** از ردیف‌های باز سفارش‌های CONFIRMED/IN_PRODUCTION/PARTIALLY_DELIVERED
   (`quantity − delivered`)؛ ردیف‌های حذف‌شده صریحاً گزارش می‌شوند، بی‌صدا حذف نمی‌شوند.
2. **موجودی قابل استفاده محصول**: فقط انبار FINISHED_GOODS فعال، کیفیت APPROVED، مالکیت OWNED؛
   قرنطینه/مسدود و امانی جداگانه نمایش داده می‌شود (قاعده «حذف موجودی غیرقابل دسترس»).
3. **رزروها**: فقط ACTIVE و منقضی‌نشده؛ رزروِ متعلق به ردیف سفارش، اول تقاضای همان ردیف را
   می‌پوشاند؛ باقی رزروها از موجودی آزاد کم می‌شوند.
4. **تخصیص موجودی آزاد** بین ردیف‌های یک قطعه به‌ترتیب سررسید (FIFO) — قطعی و تکرارپذیر.
5. **پس‌گرد WIP عملیات‌به‌عملیات** (مسیر ACTIVE، آخرین نسخه):
   `wipUsed[k] = min(آماده‌انتقال[k], خروجی لازم[k])`،
   `committedUsed[k] = min(تعهد دستور کارهای باز[k], باقیمانده)`،
   `ورودی لازم[k] = تولید جدید[k] / (1 − ضریب ضایعات[k])`،
   `درراه[k] = دریافتی + بازکار − خوراک` که نیاز خروجی عملیات قبل را کم می‌کند.
   — تعهد دستور کارهای باز (PLANNED/RELEASED/IN_PROGRESS) اعتبار می‌گیرد تا موتور برای
   کاری که از قبل برنامه‌ریزی شده، دستور کار تکراری پیشنهاد ندهد.
6. **پیشنهاد MO** = «تولید جدید» عملیات آخر (معادل محصول تکمیلی)؛ اگر صفر باشد MO پیشنهاد نمی‌شود.
7. **کسری مواد** = ورودی لازم عملیات اول × سرانه BOM، مقایسه با موجودی تأییدشده ماده
   (امانی SAPCO جدا نمایش داده می‌شود)؛ کسریِ پوشش‌پذیر با قراردادهای باز هشدار است،
   کسری بدون پوشش، ردیف را ناکارآمد می‌کند. نبود BOM = «اطلاعات ناقص»، نه فرض مقدار ۱.
8. **صلاحیت ماشین (شرط‌های سخت — عدم سازگاری هرگز تخصیص نمی‌یابد):**
   توانمندی ماشین–عملیات (MachineCapability) · وضعیت ACTIVE ماشین ·
   تناژ ≥ `required_tonnage` مرحله (اگر تعریف نشده باشد صریحاً «کنترل نشد») ·
   سازگاری قالب (`machine_die_compatibility`) و ACTIVE بودن قالب ·
   گنجایش `زمان تولید + راه‌اندازی` در ظرفیت یک روز شیفت‌های فعال.
9. **منبع زمان صریح است:** `ROUTE_STEP → CAPABILITY (۳۶۰۰/نرخ) → OPERATION_DEFAULT → MISSING`؛
   MISSING هرگز با عدد فرضی جایگزین نمی‌شود و عملیات را غیرقابل کنترل ظرفیت علامت می‌زند.
10. **رتبه‌بندی نامزدها:**زودترین تکمیل تخمینی (بر مبنای بار جاری ماشین از عملیات‌های باز +
    ظرفیت روزانه شیفت‌ها، روز-گران) ← زمان راه‌اندازی کمتر ← بار کاری کمتر؛ برای «هر» نامزد
    (واجد شرایط و غیر) دلایل فارسی ثبت می‌شود.

**شفافیت محاسبه‌شده/تخمینی:** کمیت‌های قطع‌بوش محاسبه‌شده از دفتر کل هستند؛ تاریخ‌های
تکمیل «تخمینی (روز-گران)» برچسب خورده‌اند و منبع هر زمان (`time_source`/`setup_source`)
در UI با نشان رنگی نمایش داده می‌شود.

### محدودیت‌های شفاف نسخه فعلی
- ماژول‌های اطلاعات پایه (CRUD) و کاربران/تنظیمات هنوز endpoint کامل ندارند (`501`)؛ lookups فقط‌خواندنی است.
- توکن JWT در localStorage نگه‌داری می‌شود (سادگی فاز صفر)؛ مهاجرت به httpOnly cookie
  در فازهای بعد انجام می‌شود.
- تقویم کاری روزهای تعطیل و ظرفیت سطلی روزبه‌روز هنوز مدل نشده — ظرفیت روزانه =
  مجموع مدت شیفت‌های فعال، به‌صورت صریح در `planning_params` ثبت می‌شود.

## ۹) گزارش‌های مدیریتی و کنترلی (فاز پنج)

**اصل بنیادی:** هر گزارش فقط از رکوردهای واقعی دیتابیس می‌خواند؛ هیچ مقداری ساخته نمی‌شود.
هر ستون «نوع ارزش» صریح دارد: `ACTUAL` (رکورد قطع‌بوش‌شده) / `PLANNED` (سند برنامه) /
`STANDARD` (محاسبه از BOM و زمان استاندارد) / `ESTIMATED` (برآورد بر پایه داده مرجع) —
تخمین هرگز جای اندازه‌گیری نمایش داده نمی‌شود. اطلاعات ناقص (بدون BOM، بدون نرخ ماشین،
بدون تاریخ برنامه) به‌جای فرض، صریحاً علامت می‌خورد.

**۱۳ گزارش** (`backend/src/modules/reports/`، همه GET با مجوز `reports.view`):

| کلید | گزارش | مبنای داده |
|---|---|---|
| plan-vs-actual | برنامه در مقابل عملکرد | ProductionPlanLine + تولید آخرین عملیات MO |
| order-fulfillment | اقلای سفارش مشتری | CustomerOrderLine (تحویل/باقی‌مانده/سررسیدگذشته) |
| backlog | کار در انتظار تولید | سفارش باز + WIP + MO باز + موجودی FG قابل استفاده |
| wip-by-part-operation | WIP قطعه×عملیات | ProductionOperation (همان فرمول داشبورد WIP) |
| wip-aging | قداره WIP | wip_since_at + بازه‌های سنی (نامشخص صریح) |
| material-consumption | مصرف در مقابل سرانه | دفتر کل ISSUE + رسید FG × BOM (بدون BOM = گزارش) |
| sapco-account | حساب مواد SAPCO (kg) | دفتر کل با افتتاحیه/دوره/پایانی + تطبیق + تفکیک امانی |
| inventory-valuation | ارزش‌گذاری کمّی موجودی | StockBalance — فقط کمیت (قاعده مالی تعریف نشده) |
| scrap | ضایعات قطعه×عملیات | ProductionScrap + سهم از ورودی واقعی |
| machine-workload | بار و ظرفیت ماشین | تخصیص‌ها + گزارش‌های قطع‌بوش‌شده؛ بهره‌وری فقط با داده قابل اتکا |
| production-delays | تأخیرهای تولید | سررسید واقعی سفارش/MO + planned_end عملیات |
| inventory-movements | حرکت موجودی | دفتر کل گروه‌بندی ورود/خروج/خالص |
| inventory-reconciliation | تطبیق موجودی | StockBalance ⇄ جمع علامت‌دار دفتر کل به‌تفکیک تمام بُعدها |

**داشبورد عملیاتی** (`/api/v1/dashboard/operations`): ۹ مؤلفه — سفارش فعال، تولید برنامه‌ای،
تولید واقعی، سفارش عقب‌افتاده، کسری مواد (آخرین اجرای برنامه‌ریزی)، WIP، موجودی FG، ضایعات و
بهره‌وری ماشین (فقط ماشین‌های دارای نرخ استاندارد + شیفت فعال؛ بقیه با دلیل).

**الزامات آورده‌شده:**
- فیلترها (تاریخ/قطعه/مشتری/ماشین/عملیات/ماده/انبار) با Zod سخت‌گیرانه (`.strict()`) اعتبارسنجی می‌شود.
- خروجی CSV: `?format=csv` — UTF-8 BOM، سطر عنوان + ساعت تولید جلالی + فیلترها + سرستون‌ها؛
  ضد تزریق فرمول Excel (پیشوند `'` برای سلول‌های خطرناک؛ اعداد منفی عددی می‌مانند).
- ساعت تولید گزارش در همه پاسخ‌ها (`generatedAt` UTC + `generatedAtFa` جلالی).
- جزئیات منبع: هر ردیف خلاصه `drill-down` به اسناد منبع دارد (`/reports/drill-down?kind=&id=`)
  با پیوند به صفحات برنامه/دستور کار/دفتر کل — شناسه‌های ترکیبی با کنترل UUID (400 نه 500).
- بازه پیش‌فرض صریح: بدون فیلتر تاریخ، ۳۰ روز گذشته استفاده و در `meta.defaultPeriodApplied`
  اعلام می‌شود (فرض بی‌صدا نیست).

**تضمین‌های تطبیق (آزمون خودکار — `tests/reports.test.ts`، ۱۹ آزمون):** تولید واقعی = جمع
گزارش‌های قطع‌بوش‌شده؛ WIP = تجمیع عملیات؛ حرکت خالص = دفتر کل؛ حساب SAPCO = افتتاحیه+دوره؛
موجودی رسمی = دفتر کل (و کشف موجودی منحرف‌شده)؛ مصرف واقعی = حواله‌ها؛ بهره‌وری فقط با داده
قابل اتکا؛ CSV/تزریق؛ drill-down ترکیبی.
